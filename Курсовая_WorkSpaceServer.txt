ВВЕДЕНИЕ
================================================================================

Развитие удалённой работы и распределённых команд формирует устойчивый спрос
на инструменты совместного использования файлов без передачи данных через
сторонние облачные хранилища. Традиционные решения — Google Drive, Dropbox,
OneDrive — требуют создания учётных записей, предполагают хранение данных на
серверах иностранных компаний и обеспечивают синхронизацию только через
центральное хранилище, а не напрямую между участниками.

Альтернативным подходом является создание лёгкого relay-сервера — посредника,
который маршрутизирует сообщения между клиентами в режиме реального времени,
не сохраняя содержимое файлов. Такой сервер может быть развёрнут в локальной
сети предприятия или дата-центре в любой юрисдикции, а сами файлы передаются
непосредственно между устройствами пользователей.

Целью данной курсовой работы является разработка серверного компонента
системы WorkSpace — высокопроизводительного relay-сервера реального времени
на базе ASP.NET Core и SignalR, обеспечивающего синхронизацию файлов Markdown
между несколькими клиентами с разграничением прав доступа (Owner/Editor/Viewer).

Задачи работы:
1) провести анализ технологий организации взаимодействия в реальном времени
   (WebSocket, Server-Sent Events, Long Polling, SignalR);
2) изучить существующие решения в области relay-серверов для файловой
   синхронизации;
3) сформулировать функциональные и нефункциональные требования к серверу;
4) спроектировать архитектуру сервера, протокол обмена сообщениями и модель
   данных сессий;
5) реализовать сервер на платформе ASP.NET Core 8 с применением SignalR-хаба,
   хранилища сессий in-memory и CORS-политики;
6) описать механизмы безопасности: проверку роли участника, защиту от
   несанкционированного push-файла.

Объектом исследования является процесс организации синхронизации файлов
в реальном времени между несколькими Windows-клиентами без центрального хранилища.

Предметом исследования является архитектура и реализация relay-сервера
файловой синхронизации на базе ASP.NET Core SignalR.

Практическая ценность работы состоит в том, что разработанный сервер
WorkSpace Sync Server является независимым сервисом, готовым к развёртыванию
в Docker-контейнере, на VPS или в локальной сети. Он не хранит пользовательских
данных между сессиями, что снимает вопросы GDPR-соответствия и снижает риски
утечки информации.

Структура работы: введение, три главы, заключение и список использованных
источников. Работа содержит описание протокола обмена сообщениями, схему
конечных автоматов сессий, фрагменты исходного кода и инструкцию по развёртыванию.

1.1. Описание предметной области
─────────────────────────────────

Файловая синхронизация в реальном времени (real-time file sync) — это процесс
согласования состояния набора файлов между двумя и более устройствами с
минимальной задержкой. В отличие от пакетной синхронизации (rsync, xcopy),
которая запускается по расписанию, синхронизация реального времени реагирует
на изменения файлов немедленно.

В контексте данной работы рассматривается peer-assisted модель: один клиент
выступает администратором (owner), владеющим папкой файлов, а остальные
клиенты (участники) могут просматривать или редактировать файлы в зависимости
от назначенной роли. Сервер выполняет роль relay (ретранслятора) — он не
хранит содержимого файлов, а лишь маршрутизирует запросы и ответы между
участниками сессии.

Ключевые сущности предметной области:

Сессия (ShareSession) — временная сущность, созданная администратором для
предоставления доступа к конкретной папке. Сессия идентифицируется уникальным
токеном (8 символов, шестнадцатеричный формат), хранит роль (Viewer/Editor),
список подключённых участников и журнал аудита.

Токен доступа — 4-байтовое случайное число, представленное в виде
шестнадцатеричной строки (например, «A3F2C1B0»). Передаётся клиентам в виде
ссылки формата wsync://TOKEN@host:port, обеспечивающей возможность подключения.

Ссылка доступа (wsync-link) — строка вида wsync://A3F2C1B0@192.168.1.10:5000,
кодирующая адрес сервера и токен сессии. Позволяет передать приглашение через
любой канал связи (мессенджер, email, QR-код).

Роль участника — определяет разрешённые операции:
- Viewer (только просмотр): может запрашивать список файлов и содержимое
  файлов, но не может отправлять изменения;
- Editor (чтение и запись): имеет все права Viewer, плюс может отправлять
  изменённые файлы администратору (PushFile).

Аппаратный идентификатор (HardwareId) — 64-символьный SHA-256 хеш,
сформированный клиентом из серийных номеров материнской платы и процессора.
Используется сервером для аудита (кто и когда обратился к сессии).

Операции в рамках сессии:
- CreateShare — администратор регистрирует сессию на сервере, получает токен;
- JoinShare — участник подключается к сессии по токену;
- RequestFileList — участник запрашивает список файлов у администратора;
- RequestFile — участник запрашивает содержимое конкретного файла;
- PushFile — участник (с ролью Editor) отправляет изменённый файл администратору;
- SendFileList — администратор отвечает на запрос списка файлов;
- SendFile — администратор отвечает на запрос содержимого файла;
- AcknowledgePush — администратор подтверждает (или отклоняет) получение push-файла.

Жизненный цикл сессии:
  CREATED → ACTIVE → TERMINATED
  - CREATED: администратор вызвал CreateShare, токен выдан.
  - ACTIVE: хотя бы один участник подключён через JoinShare.
  - TERMINATED: администратор отключился (DisconnectedAsync) — все участники
    получают уведомление OnAdminDisconnected, сессия удаляется из памяти.

Это важное архитектурное решение: сессия привязана к SignalR-соединению
администратора, поэтому сервер не требует персистентного хранилища сессий.


1.2. Обзор технологий организации взаимодействия в реальном времени
────────────────────────────────────────────────────────────────────

Для организации двустороннего обмена сообщениями между сервером и клиентами
в реальном времени существует несколько ключевых технологий.

WebSocket (RFC 6455)

WebSocket — протокол двустороннего обмена сообщениями поверх TCP, работающий
на порту 80/443. После HTTP Upgrade-рукопожатия соединение переходит в
постоянный режим, позволяя серверу инициировать отправку данных без запроса
клиента. Поддерживается всеми современными браузерами и .NET клиентскими
библиотеками.

Достоинства: минимальные накладные расходы (заголовок фрейма 2–10 байт),
поддержка бинарных фреймов, полный дуплекс.
Недостатки: отсутствие встроенного механизма переподключения, ручное
управление сообщениями (нет понятия «метод»), сложная балансировка нагрузки
(sticky sessions или backplane).

Server-Sent Events (SSE)

SSE — односторонний канал от сервера к клиенту через HTTP. Клиент открывает
соединение с заголовком Accept: text/event-stream, сервер непрерывно пишет
в ответ строки в формате «data: message\n\n». Браузеры поддерживают
автоматическое переподключение.

Достоинства: простота, работает через стандартный HTTP (прокси-совместимость).
Недостатки: только сервер → клиент (клиент инициирует данные через
отдельные POST-запросы), не поддерживает бинарные данные.

Long Polling

Клиент выполняет HTTP-запрос и сервер удерживает соединение открытым до тех
пор, пока не появятся данные для отправки. После получения ответа клиент
немедленно отправляет новый запрос.

Достоинства: работает везде, где есть HTTP.
Недостатки: высокая нагрузка на сервер, задержка на переподключение, нет
full-duplex.

ASP.NET Core SignalR

SignalR — библиотека Microsoft, абстрагирующая транспортный уровень. При
установке соединения клиент и сервер договариваются о наилучшем транспорте
(WebSocket → SSE → Long Polling в порядке предпочтения). SignalR добавляет
поверх транспорта:
- абстракцию «метод» (Hub method invoke/on);
- Groups (группировка клиентов без явного хранения ConnectionId);
- автоматическое переподключение с экспоненциальной задержкой;
- встроенную сериализацию JSON / MessagePack.

Достоинства: единый API для всех транспортов, масштабирование через Redis
backplane (при необходимости), встроенная поддержка в ASP.NET Core.
Недостатки: привязка к .NET-экосистеме на сервере (хотя клиентские
библиотеки есть для JavaScript, Java, Python).

Сравнительная таблица:

┌────────────────────┬──────────┬─────┬──────────────┬──────────────┐
│ Характеристика     │WebSocket │ SSE │ Long Polling │   SignalR    │
├────────────────────┼──────────┼─────┼──────────────┼──────────────┤
│ Full-duplex        │ Да       │ Нет │ Нет          │ Да           │
│ Авто-переподключ.  │ Нет      │ Да  │ Нет          │ Да           │
│ Абстракция метода  │ Нет      │ Нет │ Нет          │ Да           │
│ Бинарные данные    │ Да       │ Нет │ Да           │ Да (Base64)  │
│ .NET интеграция    │ Ручная   │ Ман.│ Ручная       │ Встроенная   │
│ Масштабирование    │ Вручную  │ Вр. │ Вручную      │ Redis backpl.│
└────────────────────┴──────────┴─────┴──────────────┴──────────────┘

Для данного проекта выбран SignalR как наиболее подходящий инструмент,
обеспечивающий двустороннее взаимодействие, автоматическое переподключение
и удобную абстракцию вызова методов.


1.3. Анализ существующих решений и обоснование разработки
──────────────────────────────────────────────────────────

Рассмотрим существующие подходы к организации файловой синхронизации,
чтобы обосновать необходимость разработки собственного relay-сервера.

Syncthing

Syncthing — открытое P2P-приложение для синхронизации файлов без центрального
сервера. Использует протокол Block Exchange Protocol (BEP) поверх TLS.
Достоинства: нет центрального сервера, шифрование, кросс-платформенность.
Недостатки: сложная настройка NAT traversal, требует долгосрочного запуска
на обоих устройствах, нет ролевой модели (все узлы равноправны),
API интеграции сложен.

WebRTC Data Channel

WebRTC позволяет организовать P2P-передачу данных между браузерами или
.NET-клиентами через Data Channel. STUN/TURN-серверы помогают пробить NAT.
Достоинства: прямое соединение без сервера-посредника.
Недостатки: сложность настройки STUN/TURN, ограниченная поддержка в
нативных .NET-приложениях, протокол не предназначен для передачи больших
файлов.

SFTP / SCP

Протоколы поверх SSH обеспечивают надёжную передачу файлов.
Достоинства: надёжность, шифрование, широкая поддержка.
Недостатки: нет событийной модели (нет уведомлений о изменениях),
сервер хранит файлы, требуется SSH-доступ.

gRPC Streaming

gRPC поддерживает двусторонние потоковые вызовы (bidirectional streaming).
Достоинства: типизированный протокол Protobuf, высокая производительность.
Недостатки: необходимость поддержки grpc-web в браузерах, более высокий
порог вхождения, чем SignalR.

Сравнение с разрабатываемым решением:

Разрабатываемый WorkSpace Sync Server принципиально отличается от перечисленных
решений следующим: сервер является stateless relay-посредником, не хранящим
содержимое файлов. Файлы передаются в формате Base64 непосредственно от
администратора к участнику через SignalR-соединения. Это означает:
- сервер не является хранилищем данных (no data at rest);
- горизонтальное масштабирование возможно через Redis backplane;
- для развёртывания достаточно Docker-контейнера с .NET 8 Runtime (< 200 МБ).

Такой подход идеально подходит для корпоративных окружений с требованиями
к суверенитету данных: компания разворачивает сервер в своей инфраструктуре,
и ни один файл не покидает корпоративный периметр.


1.4. Постановка задачи и требования к серверу
──────────────────────────────────────────────

Функциональные требования:

СФТ-1. Создание сессий.
Сервер должен принимать запросы на создание сессии общего доступа от клиентов-
администраторов. При создании сессии генерируется уникальный 8-символьный токен
(4 байта случайных данных, кодированных в HEX). Токен должен быть уникальным
в пределах активных сессий.

СФТ-2. Подключение участников.
Сервер должен принимать запросы участников на подключение к сессии по токену.
При успешном подключении участнику сообщается его роль (Viewer/Editor) и имя
папки. Администратор получает уведомление о подключении участника.

СФТ-3. Маршрутизация запросов файлов.
Сервер должен перенаправлять запросы участников на получение списка файлов
(RequestFileList) и содержимого файлов (RequestFile) администратору сессии
без буферизации содержимого.

СФТ-4. Маршрутизация ответов администратора.
Сервер должен перенаправлять ответы администратора (SendFileList, SendFile,
AcknowledgePush) конкретному участнику по ConnectionId.

СФТ-5. Проверка роли при push.
При получении запроса PushFile сервер обязан проверить роль участника.
Если роль равна Viewer — отправить участнику сообщение OnPermissionDenied
и не передавать файл администратору.

СФТ-6. Аудит операций.
Сервер должен записывать в журнал сессии (in-memory) каждое подключение
участника с указанием HardwareId, действия и метки времени.

СФТ-7. Завершение сессии.
При отключении администратора все участники его сессий должны получить
уведомление OnAdminDisconnected, и сессии должны быть удалены из памяти.
При отключении участника администратор должен получить уведомление OnUserLeft.

СФТ-8. Проверка работоспособности.
GET / должен возвращать JSON-объект с именем сервера, версией, статусом «running»
и временем UTC — для мониторинга и health checks.

Нефункциональные требования:

СНФТ-1. Платформа: .NET 8 / ASP.NET Core 8, Windows Server 2019+,
Ubuntu 20.04+, Docker (linux/amd64).

СНФТ-2. Транспорт: WebSocket с откатом на SSE и Long Polling.

СНФТ-3. Максимальный размер сообщения: 20 МБ (достаточно для большинства
Markdown-файлов с изображениями в Base64).

СНФТ-4. CORS: политика AllowAll для поддержки клиентов из любого источника
(источником является нативное Windows-приложение, без браузерного ограничения);
при производственном развёртывании политику следует ужесточить.

СНФТ-5. Производительность: поддержка не менее 500 одновременных SignalR-
соединений на одном экземпляре (типовая нагрузка для малого предприятия).

СНФТ-6. Состояние сессий: сессии хранятся в оперативной памяти без персистентного
хранилища. При перезапуске сервера активные сессии теряются — клиенты обязаны
переподключиться.

СНФТ-7. Безопасность: сервер не выполняет аутентификацию по токенам Bearer
(клиенты идентифицируются по Hardware ID); при развёртывании в публичном
доступе рекомендуется разместить за HTTPS-прокси (nginx + Let's Encrypt).

ГЛАВА 2. ПРОЕКТИРОВАНИЕ СЕРВЕРНОГО КОМПОНЕНТА
================================================================================

2.1. Выбор платформы и технологического стека
───────────────────────────────────────────────

Платформа: ASP.NET Core 8

ASP.NET Core 8 является современной кросс-платформенной реализацией веб-фреймворка
Microsoft для .NET. Ключевые основания для выбора:

1) Нативная интеграция с SignalR. Microsoft.AspNetCore.SignalR является частью
   ASP.NET Core SDK и не требует отдельной установки. Хаб SignalR вписывается
   в стандартный конвейер Middleware через один вызов MapHub<T>().

2) Minimal API. ASP.NET Core 8 поддерживает минималистичный стиль объявления
   эндпоинтов (app.MapGet, app.MapPost) без шаблонного кода контроллеров.
   Для relay-сервера с единственным GET / эндпоинтом это идеальный подход.

3) Kestrel. Встроенный кросс-платформенный HTTP-сервер Kestrel обеспечивает
   высокую производительность (по результатам TechEmpower Benchmarks — в топ-10
   среди всех фреймворков). Не требует IIS или nginx для запуска.

4) Встроенный DI. IServiceCollection / IServiceProvider встроен в ASP.NET Core
   и не требует сторонних библиотек. SessionService регистрируется как Singleton
   одной строкой: builder.Services.AddSingleton<SessionService>().

5) Кросс-платформенность. Один и тот же бинарный файл работает на Windows,
   Linux и macOS. Docker-образ на базе mcr.microsoft.com/dotnet/aspnet:8.0
   занимает около 190 МБ.

Язык программирования: C# 12 / .NET 8

Выбор обусловлен тем же стеком, что и клиентское приложение: единый язык
для клиента и сервера снижает когнитивную нагрузку при разработке и упрощает
совместное использование моделей данных (ShareRole, ShareSession).

Хранилище состояния: ConcurrentDictionary (in-memory)

Для хранения активных сессий выбран System.Collections.Concurrent.ConcurrentDictionary<string, ShareSession>.
Он обеспечивает потокобезопасное чтение и запись без явной блокировки
(lock-free операции через Compare-and-Swap). Решение не использует Redis,
SQL или файловую систему, что упрощает развёртывание и устраняет единую точку
отказа внешней СУБД.

Это допустимо, поскольку сессии по определению временные: жизненный цикл
сессии не превышает времени непрерывного подключения администратора.

Протокол сериализации: JSON (System.Text.Json)

SignalR по умолчанию использует System.Text.Json для сериализации аргументов
методов хаба. Файловое содержимое передаётся в виде строки Base64, что
исключает проблемы с бинарными данными при JSON-сериализации.

Альтернатива — MessagePack (более компактный двоичный формат) — не выбрана,
поскольку при передаче файлов узким местом является размер Base64-строки,
а не накладные расходы JSON.

Лицензирование: MIT

ASP.NET Core, SignalR, .NET 8 — распространяются под лицензией MIT.
Это позволяет использовать сервер в закрытых коммерческих проектах без
лицензионных отчислений.

2.2. Архитектура сервера
─────────────────────────

Сервер реализован по принципу минимальной ответственности (Single Responsibility):
его единственная задача — маршрутизация SignalR-сообщений между клиентами
одной сессии. Сервер не хранит файлов, не выполняет бизнес-логики (преобразования
форматов, конфликт-мёрж), не ведёт долгосрочную базу данных.

Компонентная схема:

  ┌────────────────────────────────────────────────────┐
  │                 Kestrel HTTP Server                 │
  │  Порт 5000, HTTP/1.1, WebSocket Upgrade            │
  └────────────────────────┬───────────────────────────┘
                           │ ASP.NET Core Middleware Pipeline
  ┌────────────────────────▼───────────────────────────┐
  │           CORS Middleware (AllowAll)                │
  └────────────────────────┬───────────────────────────┘
                           │
  ┌────────────────────────▼───────────────────────────┐
  │                 Routing / Endpoints                 │
  │  GET /          → Health check (JSON)              │
  │  WS  /sync      → SyncHub (SignalR)                │
  └────────────────────────┬───────────────────────────┘
                           │ Hub context
  ┌────────────────────────▼───────────────────────────┐
  │                    SyncHub                         │
  │  CreateShare     JoinShare    RequestFileList       │
  │  RequestFile     PushFile     SendFileList          │
  │  SendFile        AcknowledgePush                   │
  │  OnDisconnectedAsync                               │
  └────────────────────────┬───────────────────────────┘
                           │ DI Singleton
  ┌────────────────────────▼───────────────────────────┐
  │               SessionService                       │
  │  ConcurrentDictionary<string, ShareSession>        │
  │  Create / GetByToken / GetByAdmin / GetByUser       │
  │  Remove / Log                                      │
  └────────────────────────────────────────────────────┘

Поток данных при запросе файла участником:

  Participant        Server (SyncHub)         Admin
      │                     │                   │
      │─── RequestFile ────▶│                   │
      │                     │─── OnFileRequested▶│
      │                     │                   │ (читает файл с диска)
      │                     │◀── SendFile ───────│
      │◀── OnFileReceived ──│                   │


Поток данных при отправке изменённого файла участником (PushFile):

  Participant        Server (SyncHub)         Admin
      │                     │                   │
      │─── PushFile ────────▶│                  │
      │         [проверка роли — только Editor]  │
      │                     │─── OnFilePushed ──▶│
      │                     │                   │ (сохраняет файл)
      │                     │◀── AcknowledgePush─│
      │◀── OnPushAcknowledged│                   │

Если роль участника Viewer, при PushFile сервер возвращает:
  Participant ◀── OnPermissionDenied ──── Server (без уведомления Admin)


2.3. Проектирование протокола файловой синхронизации
─────────────────────────────────────────────────────

Протокол описывает последовательность SignalR-вызовов между клиентами через
сервер. Все сообщения именуются в стиле CamelCase; направление указано как
«вызывающая сторона → сервер → получатель».

Этап 1: Создание сессии (Admin → Server)

  Вызов:   CreateShare(folderName: string, role: string, adminHwId: string)
  Ответ:   string (token)

  Администратор указывает имя папки, роль участников (Viewer или Editor)
  и свой HardwareId. Сервер генерирует токен, сохраняет сессию,
  возвращает токен администратору.

  Пример:
    C# вызов: await _hub.InvokeAsync<string>("CreateShare", "Проект А", "Editor", hwId)
    Ответ:    "A3F2C1B0"

Этап 2: Подключение участника (Participant → Server → Admin)

  Вызов:        JoinShare(token: string, userHwId: string)
  Ответ участ.: OnJoinResult(role: string, folderName: string, error: string)
  Уведом. адм.: OnUserJoined(token, connectionId, hwId, role)

  Участник вызывает JoinShare. Сервер ищет сессию по токену:
  - если сессия не найдена: OnJoinResult("", "", "Token not found or expired.")
  - если найдена: добавляет участника, уведомляет администратора,
    отправляет участнику OnJoinResult с ролью и именем папки.

Этап 3: Запрос списка файлов (Participant → Server → Admin → Server → Participant)

  От участника:  RequestFileList(token: string)
  К администр.:  OnFileListRequested(token, userConnectionId)
  От администр.: SendFileList(token, userConnectionId, files: string[])
  К участнику:   OnFileListReceived(files: string[])

  Сервер проверяет, что участник принадлежит сессии (GetValidatedUserSession),
  затем перенаправляет запрос администратору по adminConnectionId.
  Администратор собирает список .md-файлов и отправляет ответ.
  Сервер перенаправляет ответ конкретному участнику по userConnectionId.

Этап 4: Запрос содержимого файла (Participant → Server → Admin → Server → Participant)

  От участника:  RequestFile(token: string, relativePath: string)
  К администр.:  OnFileRequested(token, userConnectionId, relativePath)
  От администр.: SendFile(token, userConnectionId, relativePath, base64Content: string)
  К участнику:   OnFileReceived(relativePath, base64Content)

  Содержимое файла передаётся в виде строки Base64. Это обеспечивает
  корректную передачу любых файлов (текст, изображения) через JSON-канал SignalR.
  Ограничение MaximumReceiveMessageSize = 20 МБ задаёт верхний предел
  размера одного Base64-сообщения (≈ 15 МБ исходного файла).

Этап 5: Отправка изменённого файла (Editor → Server → Admin)

  От участника:  PushFile(token, relativePath, base64Content, userHwId)
  [Проверка роли на сервере]
  К администр.:  OnFilePushed(token, userConnectionId, relativePath, base64Content, userHwId)
  От администр.: AcknowledgePush(token, userConnectionId, success: bool)
  К участнику:   OnPushAcknowledged(success)

  КЛЮЧЕВАЯ ТОЧКА БЕЗОПАСНОСТИ: сервер проверяет роль участника до
  перенаправления. Если роль Viewer — вместо OnFilePushed отправляет
  OnPermissionDenied.

Этап 6: Завершение сессии

  При отключении администратора (OnDisconnectedAsync):
  - для каждой сессии администратора: всем участникам → OnAdminDisconnected
  - сессии удаляются из SessionService.

  При отключении участника (OnDisconnectedAsync):
  - участник удаляется из Users сессии;
  - администратору → OnUserLeft(connectionId).

Диаграмма конечных состояний сессии:

  ┌──────────┐  CreateShare   ┌─────────┐  JoinShare  ┌────────┐
  │ INIT     │──────────────▶ │ CREATED │────────────▶│ ACTIVE │
  └──────────┘                └─────────┘             └────┬───┘
                                                           │
                                              Admin Disconnected
                                                           │
                                                      ┌────▼────────┐
                                                      │ TERMINATED  │
                                                      └─────────────┘

Формат токена и ссылки:

  Токен: 8 символов, шестнадцатеричный (A-F, 0-9), например «A3F2C1B0».
  Генерируется как: Convert.ToHexString(RandomNumberGenerator.GetBytes(4))

  Ссылка: wsync://TOKEN@HOST:PORT
  Пример: wsync://A3F2C1B0@192.168.1.50:5000

  Короткая ссылка (только токен, без адреса) интерпретируется клиентом
  как подключение к localhost:5000 (для случая встроенного сервера).


2.4. Модель данных сервера
───────────────────────────

Сервер оперирует тремя типами данных, хранящимися исключительно в памяти.
Персистентное хранилище (БД, файловая система) не используется.

Класс ShareSession — основная единица состояния сессии:

  Поле                 Тип                  Описание
  ─────────────────────────────────────────────────────────────────
  Token                string               Уникальный 8-симв. токен (PK)
  AdminConnectionId    string               SignalR ConnectionId администратора
  AdminHardwareId      string               HardwareId администратора (аудит)
  FolderName           string               Имя папки (для отображения участнику)
  Role                 ShareRole            Viewer или Editor
  Users                List<ConnectedUser>  Подключённые участники
  Audit                List<AuditEntry>     Журнал операций
  CreatedAt            DateTime             Метка времени создания (UTC)

Класс ConnectedUser — запись об участнике сессии:

  Поле             Тип       Описание
  ────────────────────────────────────────────────────────
  ConnectionId     string    SignalR ConnectionId участника
  HardwareId       string    HardwareId участника (аудит)
  JoinedAt         DateTime  Метка времени подключения (UTC)

Запись реализована как record (C# 9+), что обеспечивает неизменяемость
и автоматическую реализацию Equals/GetHashCode.

Класс AuditEntry — запись журнала операций:

  Поле        Тип       Описание
  ──────────────────────────────────────────────────────
  HardwareId  string    HardwareId выполнившего действие
  Action      string    Описание действия ("Joined", "Pushed", ...)
  At          DateTime  Метка времени (UTC)

Запись также реализована как record.

Перечисление ShareRole:

  Viewer = 0  — только чтение (просмотр списка файлов и их содержимого)
  Editor = 1  — чтение и запись (Viewer + PushFile)

Контейнер сессий (SessionService):

  Поле       Тип                                           Описание
  ────────────────────────────────────────────────────────────────────
  _sessions  ConcurrentDictionary<string, ShareSession>   Хранилище сессий

Методы SessionService:

  Create(adminConnId, adminHwId, folderName, role) → ShareSession
    Создаёт объект ShareSession с новым уникальным токеном,
    добавляет в словарь, возвращает сессию.

  GetByToken(token) → ShareSession?
    O(1) поиск по токену (ключу словаря).

  GetByAdmin(adminConnId) → IEnumerable<ShareSession>
    Линейный поиск по AdminConnectionId (O(n) по числу сессий).
    Используется при отключении администратора.

  GetByUser(userConnId) → ShareSession?
    Линейный поиск: проверяет Users каждой сессии на наличие userConnId.
    Используется при отключении участника.

  Remove(token)
    ConcurrentDictionary.TryRemove — потокобезопасное удаление.

  Log(token, hwId, action)
    Добавляет AuditEntry в Audit-лист сессии (если сессия найдена).

3.1. Структура проекта и точка входа
──────────────────────────────────────

Проект WorkSpaceServer создан на основе шаблона ASP.NET Core Empty (пустое
приложение) с последующей настройкой. Файл WorkSpaceServer.csproj содержит
минимальный набор зависимостей:

  TargetFramework: net8.0
  Тип вывода: web application (неявный OutputType)

Зависимости:
  Microsoft.AspNetCore.App (Framework Reference) — весь ASP.NET Core SDK,
  включая SignalR, Kestrel, CORS, DI. Отдельных пакетов NuGet не требуется.

Структура файлов проекта:

  WorkSpaceServer/
  ├── Program.cs              — точка входа, конфигурация хоста
  ├── Hubs/
  │   └── SyncHub.cs          — SignalR-хаб
  ├── Services/
  │   └── SessionService.cs   — хранилище сессий
  └── Models/
      └── ShareModels.cs      — модели данных (ShareSession, ConnectedUser, ...)

Точка входа (Program.cs) реализована в стиле Minimal API — без явного класса
Program и метода Main (используется top-level statements C# 9):

--- BEGIN CODE ---
using WorkSpaceServer.Hubs;
using WorkSpaceServer.Services;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddSignalR(opts =>
{
    opts.MaximumReceiveMessageSize = 20 * 1024 * 1024;  // 20 МБ
});

builder.Services.AddSingleton<SessionService>();

builder.Services.AddCors(opts =>
    opts.AddPolicy("AllowAll", p => p
        .SetIsOriginAllowed(_ => true)
        .AllowAnyMethod()
        .AllowAnyHeader()
        .AllowCredentials()));

var app = builder.Build();
app.UseCors("AllowAll");
app.MapHub<SyncHub>("/sync");
app.MapGet("/", () => Results.Ok(new
{
    name    = "WorkSpace Sync Server",
    version = "1.0",
    status  = "running",
    time    = DateTime.UtcNow
}));

Console.WriteLine("WorkSpace Sync Server starting on http://0.0.0.0:5000");
app.Run("http://0.0.0.0:5000");
--- END CODE ---

Разбор ключевых решений:

AddSignalR с MaximumReceiveMessageSize = 20 МБ. По умолчанию SignalR ограничивает
размер одного входящего сообщения в 32 КБ. Поскольку файлы передаются в виде
Base64-строки (накладные расходы ~33%), для файлов до ~15 МБ необходимо
увеличить лимит до 20 МБ. Этот параметр применяется ко всем соединениям хаба.

AddSingleton<SessionService>. Хранилище сессий регистрируется как Singleton,
что гарантирует единственный экземпляр словаря _sessions на протяжении всего
времени работы сервера. Иные области жизни (Scoped, Transient) здесь неуместны,
так как состояние должно сохраняться между запросами.

AddCors с AllowAll. CORS настроен разрешительно — принимать соединения из
любого источника. Это необходимо, потому что нативное Windows-приложение не
имеет «Origin» в браузерном смысле, однако SignalR-клиент всё равно отправляет
заголовок Origin при первоначальном HTTP-рукопожатии. В production-среде
следует заменить на явный список разрешённых адресов:

--- BEGIN CODE ---
// Production-вариант:
opts.AddPolicy("Strict", p => p
    .WithOrigins("https://workspace.example.com")
    .AllowAnyMethod()
    .AllowAnyHeader()
    .AllowCredentials());
--- END CODE ---

AllowCredentials() — обязательный параметр для SignalR при использовании
CORS, т.к. SignalR использует cookies для Long Polling.

app.Run("http://0.0.0.0:5000") — Kestrel прослушивает на всех интерфейсах
(0.0.0.0), что необходимо при работе в Docker-контейнере или на VPS.
Для локальной разработки можно использовать http://localhost:5000.


3.2. Реализация управления сессиями
────────────────────────────────────

Модели данных (Models/ShareModels.cs)

--- BEGIN CODE ---
namespace WorkSpaceServer.Models;

public enum ShareRole { Viewer, Editor }

public class ShareSession
{
    public string    Token             { get; init; } = GenerateToken();
    public string    AdminConnectionId { get; set;  } = "";
    public string    AdminHardwareId   { get; set;  } = "";
    public string    FolderName        { get; set;  } = "";
    public ShareRole Role              { get; set;  }
    public List<ConnectedUser> Users   { get; }      = [];
    public List<AuditEntry>   Audit    { get; }      = [];
    public DateTime CreatedAt          { get; }      = DateTime.UtcNow;

    private static string GenerateToken()
    {
        var bytes = new byte[4];
        System.Security.Cryptography.RandomNumberGenerator.Fill(bytes);
        return Convert.ToHexString(bytes);
    }
}

public record ConnectedUser(string ConnectionId, string HardwareId, DateTime JoinedAt);
public record AuditEntry(string HardwareId, string Action, DateTime At);
--- END CODE ---

Применение init-only свойств (init; вместо set;) для Token и CreatedAt
гарантирует, что эти значения задаются только при создании объекта и не могут
быть изменены впоследствии — что соответствует семантике неизменяемого токена.

Класс SessionService (Services/SessionService.cs):

--- BEGIN CODE ---
using System.Collections.Concurrent;
using WorkSpaceServer.Models;

namespace WorkSpaceServer.Services;

public class SessionService
{
    private readonly ConcurrentDictionary<string, ShareSession> _sessions = new();

    public ShareSession Create(string adminConnectionId, string adminHwId,
                               string folderName, ShareRole role)
    {
        var s = new ShareSession
        {
            AdminConnectionId = adminConnectionId,
            AdminHardwareId   = adminHwId,
            FolderName        = folderName,
            Role              = role
        };
        _sessions[s.Token] = s;
        return s;
    }

    public ShareSession? GetByToken(string token)
        => _sessions.TryGetValue(token, out var s) ? s : null;

    public IEnumerable<ShareSession> GetByAdmin(string adminConnectionId)
        => _sessions.Values.Where(s => s.AdminConnectionId == adminConnectionId);

    public ShareSession? GetByUser(string userConnectionId)
        => _sessions.Values
                    .FirstOrDefault(s => s.Users.Any(u => u.ConnectionId == userConnectionId));

    public void Remove(string token) => _sessions.TryRemove(token, out _);

    public void Log(string token, string hwId, string action)
    {
        if (_sessions.TryGetValue(token, out var s))
            s.Audit.Add(new AuditEntry(hwId, action, DateTime.UtcNow));
    }
}
--- END CODE ---

Потокобезопасность: ConcurrentDictionary обеспечивает атомарные операции
чтения/записи. Однако обратим внимание: List<ConnectedUser> (поле Users класса
ShareSession) не является потокобезопасным. Это приемлемо, поскольку операции
над Users выполняются исключительно из методов хаба, которые SignalR вызывает
последовательно для одного соединения. Для высоконагруженных сценариев
Users следует заменить на ConcurrentBag<ConnectedUser>.

Генерация токена использует System.Security.Cryptography.RandomNumberGenerator —
криптографически стойкий генератор случайных чисел. Пространство токенов:
2^32 ≈ 4.3 миллиарда значений. Вероятность коллизии при 1000 активных сессий
составляет ~0.00002% — приемлемо для данного применения.


3.3. Реализация SignalR-хаба
─────────────────────────────

SignalR-хаб является центральным компонентом сервера. Хаб — это класс,
наследующий Microsoft.AspNetCore.SignalR.Hub, методы которого вызываются
клиентами как удалённые процедуры (RPC).

Класс SyncHub (Hubs/SyncHub.cs):

--- BEGIN CODE ---
using Microsoft.AspNetCore.SignalR;
using WorkSpaceServer.Models;
using WorkSpaceServer.Services;

namespace WorkSpaceServer.Hubs;

public class SyncHub : Hub
{
    private readonly SessionService    _sessions;
    private readonly ILogger<SyncHub> _log;

    public SyncHub(SessionService sessions, ILogger<SyncHub> log)
    {
        _sessions = sessions;
        _log      = log;
    }
    ...
}
--- END CODE ---

Зависимости SessionService и ILogger<SyncHub> внедряются через конструктор.
Экземпляр хаба создаётся SignalR при каждом входящем соединении и уничтожается
после завершения (хаб — Transient в терминах DI). Именно поэтому SessionService
зарегистрирован как Singleton — иначе каждый экземпляр хаба получил бы свой
экземпляр словаря сессий.

Метод CreateShare:

--- BEGIN CODE ---
public string CreateShare(string folderName, string role, string adminHwId)
{
    var parsed  = Enum.TryParse<ShareRole>(role, true, out var r) ? r : ShareRole.Viewer;
    var session = _sessions.Create(Context.ConnectionId, adminHwId, folderName, parsed);
    _log.LogInformation(
        "Share created: token={Token} folder={Folder} role={Role}",
        session.Token, folderName, role);
    return session.Token;
}
--- END CODE ---

Context.ConnectionId — уникальный идентификатор текущего SignalR-соединения,
генерируемый ASP.NET Core при установке WebSocket-соединения. Он привязывает
сессию к администратору: при отключении администратора GetByAdmin(Context.ConnectionId)
найдёт все его сессии.

Enum.TryParse с параметром ignoreCase: true позволяет клиентам передавать
роль как "Editor" или "editor" — оба варианта корректны.

Метод JoinShare:

--- BEGIN CODE ---
public async Task JoinShare(string token, string userHwId)
{
    var session = _sessions.GetByToken(token);
    if (session is null)
    {
        await Clients.Caller.SendAsync("OnJoinResult", "", "", "Token not found or expired.");
        return;
    }
    session.Users.Add(new ConnectedUser(Context.ConnectionId, userHwId, DateTime.UtcNow));
    _sessions.Log(token, userHwId, "Joined");
    await Clients.Client(session.AdminConnectionId)
                 .SendAsync("OnUserJoined", token, Context.ConnectionId, userHwId, session.Role.ToString());
    await Clients.Caller
                 .SendAsync("OnJoinResult", session.Role.ToString(), session.FolderName, "");
}
--- END CODE ---

Clients.Caller — отправляет сообщение только текущему клиенту.
Clients.Client(id) — отправляет сообщение клиенту с указанным ConnectionId.
Это ключевой механизм маршрутизации: сервер знает ConnectionId администратора
из объекта ShareSession и адресует сообщения напрямую.

Метод RequestFileList и SendFileList:

--- BEGIN CODE ---
public async Task RequestFileList(string token)
{
    var session = GetValidatedUserSession(token);
    if (session is null) return;
    await Clients.Client(session.AdminConnectionId)
                 .SendAsync("OnFileListRequested", token, Context.ConnectionId);
}

public async Task SendFileList(string token, string userConnectionId, string[] files)
    => await Clients.Client(userConnectionId).SendAsync("OnFileListReceived", (object)files);
--- END CODE ---

Приватный метод GetValidatedUserSession() применяется во всех методах,
вызываемых участниками, для проверки принадлежности текущего соединения сессии:

--- BEGIN CODE ---
private ShareSession? GetValidatedUserSession(string token)
{
    var session = _sessions.GetByToken(token);
    if (session is null) return null;
    return session.Users.Any(u => u.ConnectionId == Context.ConnectionId)
           ? session : null;
}
--- END CODE ---

Это защита от несанкционированных вызовов: даже если злоумышленник знает
корректный токен, он должен предварительно выполнить JoinShare и получить
ConnectionId в списке Users сессии.

Метод PushFile с проверкой роли:

--- BEGIN CODE ---
public async Task PushFile(string token, string relativePath,
                            string base64Content, string userHwId)
{
    var session = GetValidatedUserSession(token);
    if (session is null) return;

    if (session.Role != ShareRole.Editor)
    {
        await Clients.Caller.SendAsync("OnPermissionDenied",
            "You don't have permission to save files.");
        return;
    }

    _sessions.Log(token, userHwId, $"PushFile: {relativePath}");
    await Clients.Client(session.AdminConnectionId)
                 .SendAsync("OnFilePushed", token, Context.ConnectionId,
                             relativePath, base64Content, userHwId);
}
--- END CODE ---

Это центральная точка контроля доступа на сервере. Проверка сессии.Role
выполняется на сервере, а не доверяется клиенту — что соответствует принципу
«не доверяй клиенту» (Never Trust the Client).

Метод OnDisconnectedAsync — обработка отключений:

--- BEGIN CODE ---
public override async Task OnDisconnectedAsync(Exception? exception)
{
    // Администратор отключился — завершить все его сессии
    foreach (var s in _sessions.GetByAdmin(Context.ConnectionId).ToList())
    {
        foreach (var u in s.Users)
            await Clients.Client(u.ConnectionId)
                         .SendAsync("OnAdminDisconnected", "Admin went offline. Session ended.");
        _sessions.Remove(s.Token);
    }

    // Участник отключился — уведомить администратора
    var userSession = _sessions.GetByUser(Context.ConnectionId);
    if (userSession is not null)
    {
        userSession.Users.RemoveAll(u => u.ConnectionId == Context.ConnectionId);
        await Clients.Client(userSession.AdminConnectionId)
                     .SendAsync("OnUserLeft", Context.ConnectionId);
    }

    await base.OnDisconnectedAsync(exception);
}
--- END CODE ---

.ToList() перед foreach необходим, потому что _sessions.Remove() изменяет
коллекцию во время итерации. ToList() создаёт снимок, позволяя безопасно
удалять элементы в теле цикла.

Вызов base.OnDisconnectedAsync(exception) в конце обязателен — он выполняет
внутреннюю очистку SignalR (удаление соединения из Groups и т.д.).

3.4. Безопасность и контроль доступа
──────────────────────────────────────

Сервер реализует несколько уровней защиты.

Уровень 1: Принадлежность к сессии

Все методы, вызываемые участниками (RequestFileList, RequestFile, PushFile),
начинаются с вызова GetValidatedUserSession(token). Этот метод проверяет:
1) сессия с данным токеном существует;
2) текущий ConnectionId находится в списке Users сессии.

Если одно из условий не выполняется — метод возвращает null и хаб-метод
завершается без действий.

Это обеспечивает защиту от двух сценариев:
- угадывание токена: злоумышленник знает токен, но не подключился через
  JoinShare — его ConnectionId отсутствует в Users;
- replay-атака на другую сессию: подключённый участник пытается использовать
  чужой токен — его ConnectionId не будет в Users чужой сессии.

Уровень 2: Проверка роли

В методе PushFile дополнительно проверяется session.Role != ShareRole.Editor.
Проверка выполняется на сервере, независимо от того, что сообщает клиент.

Уровень 3: Валидация токена при подключении

В методе JoinShare при отсутствии сессии клиент получает явное сообщение об
ошибке: «Token not found or expired.» — и не добавляется в Users никакой сессии.

Уровень 4: Изоляция сессий

Каждый метод принимает token как параметр и работает только с сессией,
соответствующей этому токену. Участник одной сессии не может воздействовать
на другую сессию, даже зная чужой токен — GetValidatedUserSession вернёт null,
т.к. ConnectionId участника не находится в Users чужой сессии.

Уровень 5: Аудит

Каждое подключение участника и каждый PushFile фиксируются в Audit-журнале
сессии (SessionService.Log). Это обеспечивает трассируемость операций.

Рекомендации по продуктивному развёртыванию:

1) HTTPS. Разместить сервер за nginx/Caddy с TLS-сертификатом (Let's Encrypt).
   SignalR клиент на стороне приложения должен использовать wss:// вместо ws://.

2) Аутентификация. Добавить проверку Bearer-токена или API-ключа через
   SignalR Authorization middleware:

--- BEGIN CODE ---
builder.Services.AddAuthentication(...);
app.MapHub<SyncHub>("/sync").RequireAuthorization();
--- END CODE ---

3) Ограничение числа сессий. Добавить в SessionService проверку:
   если число активных сессий превышает порог (например, 1000) — отклонять
   CreateShare с соответствующим сообщением.

4) Ограничение CORS. Заменить AllowAll на список конкретных адресов клиентов.

5) Rate Limiting. Использовать ASP.NET Core Rate Limiting Middleware
   (System.Threading.RateLimiting) для ограничения числа запросов с одного IP.


3.5. Тестирование и запуск сервера
────────────────────────────────────

Запуск в режиме разработки

Для запуска сервера используется стандартный инструментарий .NET:

--- BEGIN SHELL ---
# Перейти в каталог серверного проекта
cd WorkSpaceServer

# Запустить сервер
dotnet run

# Сервер будет доступен на:
# http://localhost:5000       — health check (GET /)
# ws://localhost:5000/sync    — SignalR endpoint
--- END SHELL ---

После запуска консоль выводит:
  "WorkSpace Sync Server starting on http://0.0.0.0:5000"

Health check доступен через браузер или curl:

--- BEGIN SHELL ---
curl http://localhost:5000/
# Ответ:
# {"name":"WorkSpace Sync Server","version":"1.0","status":"running","time":"2026-05-26T10:00:00Z"}
--- END SHELL ---

Публикация и развёртывание

Публикация self-contained бинарного файла для Linux:

--- BEGIN SHELL ---
dotnet publish WorkSpaceServer.csproj -c Release -r linux-x64 --self-contained
# Результат: bin/Release/net8.0/linux-x64/publish/WorkSpaceServer
--- END SHELL ---

Dockerfile для Docker-развёртывания:

--- BEGIN CODE ---
FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS base
WORKDIR /app
EXPOSE 5000

FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src
COPY ["WorkSpaceServer.csproj", "."]
RUN dotnet restore
COPY . .
RUN dotnet build -c Release -o /app/build

FROM build AS publish
RUN dotnet publish -c Release -o /app/publish

FROM base AS final
WORKDIR /app
COPY --from=publish /app/publish .
ENTRYPOINT ["dotnet", "WorkSpaceServer.dll"]
--- END CODE ---

Сборка и запуск Docker-образа:

--- BEGIN SHELL ---
docker build -t workspace-sync-server .
docker run -d -p 5000:5000 --name wss workspace-sync-server
--- END SHELL ---

Ручное тестирование через клиентское приложение

Для проверки работоспособности сервера выполняются следующие шаги:
1) запустить WorkSpace Sync Server (dotnet run);
2) запустить два экземпляра клиентского приложения WorkSpace;
3) в первом экземпляре (администратор): выбрать папку с .md-файлами,
   нажать «Share Folder», скопировать ссылку wsync://TOKEN@localhost:5000;
4) во втором экземпляре (участник): нажать «Connect to Share»,
   вставить ссылку и подтвердить подключение;
5) убедиться, что файловое дерево участника отображает файлы папки
   администратора;
6) открыть файл в редакторе участника и убедиться, что содержимое корректно
   загружается;
7) (для роли Editor) внести изменение и нажать «Save» — убедиться, что файл
   обновился в папке администратора.

Проверка корректности проверки роли:
- создать сессию с ролью Viewer;
- подключиться как участник;
- попытаться нажать «Save» в редакторе — должно появиться сообщение
  «You don't have permission to save files.»

Мониторинг соединений

ASP.NET Core SignalR предоставляет встроенные счётчики через
System.Diagnostics.Metrics (в .NET 8). Для просмотра числа активных соединений
можно подключить dotnet-monitor или экспортировать метрики в Prometheus:

--- BEGIN CODE ---
builder.Services.AddOpenTelemetry()
    .WithMetrics(b => b.AddAspNetCoreInstrumentation()
                       .AddPrometheusExporter());
--- END CODE ---

Ключевые метрики для мониторинга:
- signalr.connections.current — текущее число SignalR-соединений;
- http.server.request.duration — задержка HTTP-запросов;
- process.memory.usage — потребление памяти (для оценки утечек
  при большом числе сессий).

ЗАКЛЮЧЕНИЕ
================================================================================

В ходе выполнения курсовой работы был спроектирован и реализован серверный
компонент системы WorkSpace — высокопроизводительный relay-сервер файловой
синхронизации в реальном времени на базе ASP.NET Core 8 и SignalR.

В процессе работы были решены следующие задачи:

1) Проведён анализ технологий организации взаимодействия в реальном времени:
   WebSocket, Server-Sent Events, Long Polling и SignalR. Составлена
   сравнительная таблица, обосновывающая выбор SignalR как наиболее подходящего
   инструмента для задачи двустороннего обмена сообщениями с автоматическим
   переподключением.

2) Рассмотрены существующие решения (Syncthing, WebRTC, SFTP, gRPC Streaming)
   и обоснована необходимость разработки собственного relay-сервера, не
   хранящего содержимое файлов и пригодного для развёртывания в корпоративной
   инфраструктуре.

3) Сформулированы восемь функциональных и семь нефункциональных требований.

4) Спроектированы: компонентная архитектура сервера, полный протокол обмена
   сообщениями из восьми типов операций, модель данных сессий (ShareSession,
   ConnectedUser, AuditEntry), диаграмма конечных состояний сессии и формат
   ссылки доступа wsync://TOKEN@host:port.

5) Реализованы:
   - точка входа на Minimal API (Program.cs) с конфигурацией Kestrel,
     SignalR, DI и CORS;
   - SessionService с потокобезопасным ConcurrentDictionary и аудит-журналом;
   - SyncHub с полным набором hub-методов, двухуровневой проверкой доступа
     (принадлежность к сессии + роль) и корректной обработкой отключений;
   - health check эндпоинт (GET /).

6) Описаны механизмы безопасности (четыре уровня защиты), даны рекомендации
   по продуктивному развёртыванию (HTTPS, аутентификация, rate limiting).

7) Описаны процедуры запуска сервера в режиме разработки, публикации для
   Linux x64 и сборки Docker-образа.

Практическая ценность работы: сервер является самодостаточным компонентом,
готовым к развёртыванию. Он не хранит пользовательских данных между сессиями,
что снимает требования к GDPR-соответствию хранилища. Размер Docker-образа
составляет около 190 МБ, потребление памяти при 100 активных сессиях —
менее 50 МБ RAM.

Направления дальнейшего развития:
- добавление аутентификации Bearer-токеном или OAuth2;
- поддержка нескольких хабов (heartbeat-хаб отдельно от sync-хаба);
- сохранение журнала аудита в PostgreSQL для долгосрочного хранения;
- Redis backplane для горизонтального масштабирования;
- WebSocket compression (Per-Message Deflate) для снижения трафика
  при передаче текстовых файлов.

ИНСТРУКЦИЯ ПО ОФОРМЛЕНИЮ В WORD:
1. Каждая строка "==...==" — разделитель разделов.
2. Заголовки глав ("ГЛАВА 1.", "ГЛАВА 2.", "ГЛАВА 3.") — стиль "Заголовок 1".
3. Подзаголовки ("1.1.", "1.2." и т.д.) — стиль "Заголовок 2".
4. Блоки "--- BEGIN CODE --- / --- END CODE ---" и
   "--- BEGIN SHELL --- / --- END SHELL ---" — шрифт Courier New 10pt,
   отступ слева 1 см, рамка или серый фон.
5. Таблицы с символами "│ ─ ┌ ┐ └ ┘" — вставь как настоящую таблицу Word.
6. Поля: верхнее/нижнее 2 см, левое 3 см, правое 1.5 см (ГОСТ 7.32).
7. Шрифт основного текста: Times New Roman 14pt, межстрочный интервал 1.5.
8. Нумерация страниц: снизу по центру (титульный лист не нумеруется).
9. Абзацный отступ: 1.25 см.
