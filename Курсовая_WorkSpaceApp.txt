ВВЕДЕНИЕ
================================================================================

В современном мире объём информации, с которым приходится работать специалистам
в различных областях, постоянно растёт. Студенты, разработчики, исследователи
и менеджеры ежедневно создают десятки заметок, фиксируют задачи, структурируют
данные в таблицах и формируют базы знаний. Для эффективного управления этим
потоком информации необходимы специализированные инструменты.

Существующие решения — такие как Microsoft OneNote, Notion, Obsidian, Joplin —
решают часть задач, однако обладают рядом ограничений: зависимостью от облачных
сервисов с иностранной юрисдикцией, закрытым исходным кодом, платным доступом
к ключевым функциям или ориентацией исключительно на веб-платформу. Отдельную
проблему представляет отсутствие нативной поддержки Windows-экосистемы: большинство
конкурирующих продуктов реализованы как веб-приложения, обёрнутые в Electron, что
приводит к высокому потреблению оперативной памяти и замедленному старту.

Целью данной курсовой работы является разработка нативного настольного приложения
WorkSpace для операционной системы Windows, ориентированного на управление заметками,
пользовательскими базами данных и напоминаниями. Приложение реализует офлайн-первый
подход: все данные хранятся локально в базе SQLite, а пользователь идентифицируется
уникальным аппаратным идентификатором без обязательной регистрации учётной записи.

Задачи работы:
1) провести анализ предметной области и существующих аналогов;
2) сформулировать требования к разрабатываемому приложению;
3) спроектировать архитектуру приложения, схему базы данных и состав модулей;
4) реализовать приложение с применением паттерна MVVM и контейнера внедрения
   зависимостей на платформе WinUI 3 / Windows App SDK;
5) описать реализованные модули и интерфейс пользователя.

Объектом исследования является процесс управления персональными знаниями
на настольном ПК под управлением Windows 10/11.

Предметом исследования является архитектура и реализация нативного Windows-приложения
для управления заметками, таблицами, напоминаниями и файловым деревом.

Практическая ценность работы состоит в том, что разработанное приложение WorkSpace
представляет собой полнофункциональный инструмент, готовый к использованию:
оно включает редактор заметок в формате Markdown с экспортом в PDF, встроенный
конструктор пользовательских таблиц, систему тегов, навигатор по файловой системе
и механизм напоминаний.

Структура работы: введение, три главы, заключение и список использованных источников.
Работа содержит описание архитектурных решений, схему базы данных, фрагменты исходного
кода и описание пользовательского интерфейса.

1.1. Описание предметной области
─────────────────────────────────

Управление персональными знаниями (Personal Knowledge Management, PKM) — это
совокупность методов и инструментов для сбора, организации, хранения, поиска
и использования информации в профессиональной и повседневной деятельности.
С ростом популярности методологии «второго мозга» (Building a Second Brain,
Тиаго Форте) интерес к PKM-инструментам резко возрос: по данным аналитической
компании Statista, мировой рынок приложений для работы с заметками в 2024 году
превысил 2,5 млрд долларов и продолжает расти.

В рамках предметной области можно выделить следующие ключевые сущности:

Заметка (Note) — основная единица хранения информации. Имеет заголовок,
содержимое (как правило, в формате Markdown или HTML), дату создания и дату
последнего изменения, а также принадлежность владельцу.

Тег (Tag) — метка, позволяющая группировать заметки или файлы по тематике
независимо от их физического расположения. Тег имеет имя и цвет.

Пользовательская таблица (Dynamic Table) — структурированный набор данных
со схемой, определяемой пользователем в виде столбцов с типами данных
(текст, число, дата, булево значение, список выбора).

Напоминание (Reminder) — запись, связанная с датой и приоритетом, служащая
для отслеживания задач и дедлайнов.

Журнал изменений (ChangeLog) — неизменяемая история создания, редактирования
и удаления заметок и таблиц, обеспечивающая аудиторскую прозрачность.

Физический файл (.md) — файл на диске в формате Markdown, который может быть
открыт в редакторе и помечен тегами без привязки к базе данных.

Аппаратный идентификатор (Hardware ID) — уникальный хеш, получаемый из
серийных номеров материнской платы и процессора. Используется как первичный
ключ пользователя без необходимости регистрации.

Взаимосвязи между сущностями подчиняются следующим правилам:
- Заметка принадлежит одному владельцу (связь определяется по HardwareId).
- Заметка может иметь множество тегов (связь «многие ко многим» через NoteTag).
- Файл на диске может иметь множество тегов (связь через FileTag).
- Каждое изменение заметки или таблицы фиксируется записью в ChangeLog.
- Пользовательская таблица содержит произвольное число строк (DynamicRow),
  данные каждой из которых хранятся в виде JSON-объекта.


1.2. Обзор существующих аналогов
──────────────────────────────────

Для обоснования необходимости разработки собственного решения проведём
сравнительный анализ ключевых конкурентов.

Microsoft OneNote
Достоинства: глубокая интеграция с Windows и пакетом Microsoft 365,
поддержка рукописного ввода, совместная работа через OneDrive.
Недостатки: данные хранятся в облаке (требуется аккаунт Microsoft),
интерфейс перегружен, нет поддержки Markdown, отсутствует конструктор
пользовательских таблиц с произвольными типами столбцов, экспорт в PDF
ограничен.

Notion
Достоинства: гибкость структуры, базы данных, богатые блоки контента,
веб-доступ с любого устройства.
Недостатки: полностью облачное решение (данные на серверах компании
в юрисдикции США), обязательная регистрация, бесплатный тариф существенно
ограничен, Electron-обёртка потребляет 300–500 МБ оперативной памяти,
медленный запуск, нет нативной поддержки Windows API.

Obsidian
Достоинства: локальное хранение в папке Markdown-файлов, граф связей,
богатая экосистема плагинов, открытый формат данных.
Недостатки: интерфейс не является нативным (Electron), базовые функции
синхронизации и публикации платные, нет встроенного конструктора
структурированных таблиц, отсутствует жёстко typed база данных с EF Core.

Joplin
Достоинства: открытый исходный код, локальное хранение, шифрование,
поддержка Markdown.
Недостатки: Electron-приложение, синхронизация требует внешнего облака
(Dropbox, WebDAV), нет пользовательских таблиц, интерфейс устарел.

UpNote
Достоинства: нативный WinUI-дизайн, приятный интерфейс, теги.
Недостатки: частично платное решение, нет пользовательских таблиц,
нет аппаратной идентификации, нет файлового дерева с тегами.

Сравнительная таблица аналогов:

интерфейс Windows, офлайн-хранение, пользовательские таблицы, теги файловой
системы и полный аудит изменений одновременно. Это подтверждает актуальность
разработки приложения WorkSpace.


1.3. Постановка задачи и требования к приложению
─────────────────────────────────────────────────

На основе анализа предметной области и аналогов сформулируем требования
к разрабатываемому приложению.

Функциональные требования:

ФТ-1. Редактор заметок.
Приложение должно предоставлять редактор заметок с поддержкой формата Markdown,
включая инструментальную панель с кнопками форматирования (полужирный, курсив,
заголовки, списки, ссылки, изображения). Редактор должен автоматически сохранять
изменения при каждом вводе символа.

ФТ-2. Управление тегами.
Приложение должно поддерживать создание цветных тегов и их назначение как
заметкам в базе данных, так и файлам Markdown на диске. Фильтрация по тегам
должна быть доступна из боковой панели.

ФТ-3. Пользовательские таблицы.
Приложение должно позволять создавать произвольные таблицы с определяемыми
пользователем столбцами следующих типов: текст (Text), число (Number), дата
(Date), булево значение (Boolean) и список выбора (Select). Должны поддерживаться
добавление, редактирование и удаление строк, а также переименование и смена типа
столбцов.

ФТ-4. Напоминания.
Приложение должно содержать раздел напоминаний с возможностью создания записей
с заголовком, датой, приоритетом и признаком выполнения, а также их фильтрацией.

ФТ-5. Файловое дерево.
Приложение должно отображать дерево файловой системы для выбранной папки,
позволять открывать файлы .md в редакторе, назначать им теги через контекстное
меню и закреплять часто используемые папки.

ФТ-6. Экспорт в PDF.
Приложение должно обеспечивать экспорт текущей заметки в PDF-документ с
поддержкой форматирования (заголовки, списки, таблицы, выделение текста).

ФТ-7. История изменений.
Каждое создание, изменение или удаление заметки и таблицы должно фиксироваться
в журнале изменений. Записи журнала должны быть неизменяемыми (immutable).

ФТ-8. Профиль пользователя.
Приложение должно идентифицировать пользователя по аппаратному идентификатору,
формируемому из серийных номеров материнской платы и процессора, без обязательной
регистрации. Должна быть предусмотрена возможность задать отображаемое имя.

ФТ-9. Мониторинг хранилища.
Приложение должно отображать степень заполнения базы данных и блокировать
синхронизацию при достижении лимита в 1 ГБ.

ФТ-10. Поддержка тем оформления.
Приложение должно поддерживать переключение между светлой и тёмной темой
оформления в режиме реального времени.

Нефункциональные требования:

НФТ-1. Платформа: Windows 10 версии 1809 (сборка 17763) и выше, Windows 11,
архитектуры x86, x64, arm64.

НФТ-2. Автономность: приложение должно функционировать без подключения к сети;
все данные хранятся локально в SQLite по пути
%LOCALAPPDATA%\WorkSpaceApp\workspace.db.

НФТ-3. Производительность: запуск приложения должен занимать не более 5 секунд
на типовом устройстве (Intel Core i5 / 8 ГБ RAM / SSD).

НФТ-4. Нативный интерфейс: UI должен быть реализован с использованием WinUI 3
и соответствовать гайдлайнам Fluent Design System.

НФТ-5. Сопровождаемость кода: архитектура должна следовать паттерну MVVM,
кодовая база — содержать не более 30 связанных файлов с плоской структурой
директорий (flat layout).

НФТ-6. Надёжность: приложение не должно терять данные при аварийном завершении;
изменения должны фиксироваться в БД до отображения в UI.

НФТ-7. Лицензионная чистота: все используемые сторонние библиотеки должны
распространяться под лицензиями MIT, Apache 2.0 или аналогичными, допускающими
использование в закрытом коде.

2.1. Выбор платформы и технологического стека
───────────────────────────────────────────────

При выборе технологий руководствовались следующими критериями: нативный внешний
вид, высокая производительность, поддержка современных версий .NET, наличие
зрелых библиотек для работы с базой данных и генерации документов.

Платформа: WinUI 3 / Windows App SDK 1.5

WinUI 3 является следующим поколением UI-фреймворка от Microsoft, пришедшим
на смену UWP (Universal Windows Platform). Ключевые преимущества:
- нативные элементы управления Fluent Design System без Electron-обёртки;
- поддержка Windows 10 (начиная со сборки 17763) и Windows 11;
- DispatcherQueue для безопасного обновления UI из асинхронных потоков;
- встроенная поддержка WebView2 (браузерный движок на базе Chromium)
  для размещения веб-компонентов внутри нативного окна.

Язык программирования: C# 12 / .NET 8

.NET 8 является LTS-версией (поддержка до ноября 2026 г.) и предоставляет:
- современный синтаксис C# 12 (primary constructors, collection expressions);
- высокую производительность благодаря JIT-компилятору RyuJIT;
- богатую стандартную библиотеку для работы с файлами, JSON, криптографией.

ORM и база данных: Entity Framework Core 8 + SQLite

EF Core 8 обеспечивает строго типизированный доступ к SQLite без необходимости
писать SQL-запросы вручную. Файловая база SQLite хранится в %LOCALAPPDATA%,
что обеспечивает изоляцию данных между пользователями и не требует установки
сервера СУБД. Ограничение в 1 ГБ выбрано как компромисс между практической
полезностью (достаточно для хранения тысяч заметок) и надёжностью (предотвращение
деградации SQLite при очень больших объёмах BLOB-данных).

MVVM-фреймворк: CommunityToolkit.Mvvm 8.2

Библиотека CommunityToolkit.Mvvm предоставляет source generators, генерирующие
шаблонный код MVVM во время компиляции. Атрибут [ObservableProperty] создаёт
публичное свойство-обёртку с вызовом PropertyChanged, атрибут [RelayCommand] —
реализацию ICommand. Это сокращает количество бойлерплейт-кода на 60–70%.

Редактор Markdown: EasyMDE (JavaScript)

EasyMDE — популярный open-source редактор Markdown на JavaScript (лицензия MIT).
Он размещается внутри WebView2: нативное приложение загружает HTML-страницу
с инициализированным экземпляром EasyMDE. Коммуникация между C# и JS
осуществляется через WebMessageReceived (JS → C#) и ExecuteScriptAsync (C# → JS).
Такой подход позволяет использовать богатый экосистемой инструмент без портирования
его логики на C#.

PDF-генератор: QuestPDF 2024.3

QuestPDF — .NET-библиотека для генерации PDF-документов с Fluent API. Она не
зависит от Microsoft Word или Ghost Script, работает полностью локально и
поддерживает Unicode, таблицы, изображения и пользовательские шрифты. Лицензия:
MIT (для открытых проектов), Community (для закрытых с оборотом до $1 млн).

DI-контейнер: Microsoft.Extensions.Hosting

Generic Host обеспечивает жизненный цикл приложения, конфигурацию и DI-контейнер
(IServiceCollection). Его использование в desktop-приложении вместо упрощённых
альтернатив (SimpleInjector, Autofac) позволяет переиспользовать паттерны,
хорошо знакомые разработчикам ASP.NET Core, и пользоваться готовыми расширениями
(AddDbContext, AddSingleton, AddTransient).

SignalR-клиент: Microsoft.AspNetCore.SignalR.Client 8.0

ASP.NET Core SignalR предоставляет клиентскую библиотеку с автоматическим
переподключением и транспортами WebSocket / Server-Sent Events / Long Polling.
В приложении используется для heartbeat-соединения и файловой синхронизации.

Встроенный relay-сервер: ASP.NET Core (in-process)

Для возможности создания общего доступа к папке без внешнего сервера в приложение
встроен компактный ASP.NET Core WebApplication, запускаемый на порту 5000.
Это позволяет одному пользователю выступать администратором папки без разворачивания
отдельного серверного процесса.

Аппаратная идентификация: System.Management (WMI) + SHA-256

Для идентификации пользователя без учётной записи используются WMI-запросы
к Win32_ComputerSystemProduct (серийный номер материнской платы) и Win32_Processor
(ProcessorId). Конкатенация значений хешируется SHA-256 — получается 64-символьный
шестнадцатеричный идентификатор, стабильный при переустановке Windows и смене
пользователя.

2.4. Описание модулей системы

Приложение включает 25 модулей клиентской части, которые по функциональному
назначению разделены на четыре группы.

Группа 1. Точка входа и навигационная оболочка

App.xaml.cs — точка входа приложения. Класс App наследует Microsoft.UI.Xaml.Application.
В переопределённом методе OnLaunched() последовательно:
1) регистрируется глобальный обработчик UnhandledException;
2) строится DI-хост вызовом BuildHost();
3) инициализируется схема БД (Database.EnsureCreatedAsync);
4) загружается профиль пользователя (UserProfileService.LoadAsync);
5) открывается главное окно.

MainWindow.xaml / MainWindow.xaml.cs — навигационная оболочка. Реализует:
- NavigationView с боковой панелью;
- переключение страниц по тегу навигационного элемента;
- управление закреплёнными папками (добавление, удаление, восстановление при старте);
- секцию «Shared Access» для папок с общим доступом;
- статус-бар с прогрессом хранилища и индикатором соединения;
- диалог изменения имени пользователя.

Группа 2. Страницы (Views/Pages)

NoteEditorPage.xaml / NoteEditorPage.xaml.cs — центральная страница приложения.
Содержит WebView2 с редактором EasyMDE, файловое дерево, панель тегов и
кнопки экспорта. Code-behind отвечает за:
- инициализацию WebView2 и загрузку HTML-шаблона редактора;
- двустороннюю коммуникацию C#↔JS (получение текста через WebMessageReceived,
  обновление через ExecuteScriptAsync);
- автосохранение при каждом изменении;
- диалоги создания общего доступа к папке и подключения к удалённой папке.

DatabasePage.xaml / DatabasePage.xaml.cs — страница управления таблицами.
Содержит список таблиц (встроенные: Notes, Reminders, FileTags; плюс
пользовательские) и GridView строк выбранной таблицы. Code-behind реализует
диалоги создания таблицы, добавления/редактирования строк, переименования
столбцов.

RemindersPage.xaml / RemindersPage.xaml.cs — страница напоминаний.
Отображает ListView напоминаний с фильтром по типу (All / Local / Synced).

FileTreeNodeView.xaml / FileTreeNodeView.xaml.cs — UserControl для рекурсивного
отображения одного узла файлового дерева (папки или файла). Реализует
контекстное меню с функциями «Share Folder» и назначения тегов.

Группа 3. ViewModels

NoteEditorViewModel.cs управляет:
- загрузкой заметки из БД (LoadNoteAsync) или файла с диска (LoadFromFileAsync);
- сохранением с фиксацией в ChangeLog (SaveAsync, SaveToFileAsync);
- управлением тегами заметки (AddTagAsync, RemoveTagAsync);
- генерацией PDF (GeneratePdfAsync через QuestPDF);
- обновлением списка истории изменений (RefreshChangeLogsAsync).

DatabaseViewModel.cs управляет:
- динамическим списком таблиц (встроенные + пользовательские);
- загрузкой данных активной таблицы (LoadTableDataAsync);
- CRUD-операциями со строками и столбцами (AddRowAsync, EditRowAsync,
  DeleteRowAsync, CreateTableAsync, DeleteTableAsync, RenameColumnAsync);
- конвертацией столбца в тип Boolean (MakeColumnCheckboxAsync);
- мгновенным переключением чекбокса (ToggleCheckboxAsync).

RemindersViewModel.cs управляет:
- хранением напоминаний в памяти (ObservableCollection);
- фильтрацией по типу (SetFilter: All/Local/Synced);
- CRUD напоминаний (AddReminder, DeleteReminder).
Напоминания не сохраняются в БД между сессиями (хранятся только в памяти).

FileTreeViewModel.cs управляет:
- построением дерева файловой системы из DirectoryInfo (LoadDirectory);
- рекурсивной загрузкой тегов файлов из БД (LoadTagsForTreeAsync);
- обработкой кликов по узлам (NodeClicked — toggle папки / открытие файла);
- переключением тегов файлов (ToggleFileTagAsync);
- отображением удалённых файлов (LoadRemoteFiles, ClearRemoteFiles).

Группа 4. Сервисы

HardwareIdService.cs — генерирует и кеширует аппаратный идентификатор
через WMI-запросы к Win32_ComputerSystemProduct и Win32_Processor.
Результат (SHA-256 хеш) кешируется в приватном поле и используется как
первичный ключ пользователя во всём приложении.

UserProfileService.cs — загружает и сохраняет отображаемое имя пользователя
в таблице HardwareRegistrations. При изменении имени генерирует событие
DisplayNameChanged, на которое подписывается MainWindow для обновления
навигационной панели.

StorageMonitorService.cs — предоставляет текущий размер базы данных,
свободное место на диске, коэффициент заполнения (0–1) и флаг превышения
лимита. Используется статус-баром MainWindow для отображения прогресс-бара.

SignalRService.cs — heartbeat-клиент. Подключается к удалённому хабу,
отправляет сигнал каждые 15 секунд (HardwareId, статус, свободное место,
DisplayName), принимает статус владельца (OwnerStatusChanged), поддерживает
загрузку файлов с тройной проверкой:
1) роль вызывающего — Owner или Editor (Viewer не может скачивать);
2) размер БД ниже лимита 1 ГБ;
3) владелец онлайн.

SyncService.cs — клиент файловой синхронизации. Реализует полный
SignalR-протокол создания/подключения к сессии, запроса и отправки списков
файлов, запроса и отправки содержимого файлов. Ссылка доступа имеет формат
wsync://TOKEN@host:port.

SyncAdminSession.cs — обслуживает входящие запросы участников на стороне
администратора. При получении OnFileListRequested сканирует папку и отправляет
список .md-файлов; при OnFilePushed сохраняет файл с защитой от path-traversal
(GetSafePath) и записывает аудит в ChangeLog.

PinnedFoldersService.cs — сохраняет список закреплённых папок в файл
%LOCALAPPDATA%\WorkSpaceApp\pinned_folders.json в формате JSON-массива
объектов {name, path}.

SharedFolderManager.cs — хранит в памяти коллекцию активных общих папок
(ObservableCollection<SharedFolderEntry>). Каждая запись содержит токен,
роль, имя удалённой папки, URL сервера и отображаемое имя.

InProcessSyncServer.cs — встроенный relay-сервер ASP.NET Core. Запускается
на http://0.0.0.0:5000 при первом создании общего доступа (идемпотентно).
Не требует внешнего серверного процесса и работает в адресном пространстве
клиентского приложения. Содержит EmbeddedSyncHub (сигналR-хаб) и
EmbeddedSessionService (хранилище сессий in-memory).

--- BEGIN CODE ---
private static IHost BuildHost() =>
    Host.CreateDefaultBuilder()
        .ConfigureServices((_, services) =>
        {
            services.AddDbContext<AppDbContext>(opt =>
                opt.UseSqlite($"Data Source={AppDbContext.GetDatabaseFilePath()}"));

            services.AddSingleton<IHardwareIdService, HardwareIdService>();
            services.AddSingleton<IUserProfileService, UserProfileService>();
            services.AddSingleton<IStorageMonitorService, StorageMonitorService>();
            services.AddSingleton<ISignalRService, SignalRService>();
            services.AddSingleton<ISyncService, SyncService>();
            services.AddSingleton<SharedFolderManager>();
            services.AddSingleton<PinnedFoldersService>();

            services.AddTransient<NoteEditorViewModel>();
            services.AddTransient<DatabaseViewModel>();
            services.AddTransient<CollaborationViewModel>();
            services.AddSingleton<RemindersViewModel>();

            services.AddSingleton<MainWindow>();
        })
        .Build();
--- END CODE ---

После построения хоста выполняется последовательная инициализация:
создание схемы БД, загрузка профиля пользователя, открытие главного окна.

Подход позволяет разрешать зависимости через App.Services.GetRequiredService<T>()
в любой точке приложения, не прибегая к паттерну Service Locator в бизнес-логике
(ViewModels получают зависимости через конструктор).

3.3. Реализация сервисов
─────────────────────────

Сервис аппаратной идентификации (HardwareIdService)

Идентификатор формируется из двух WMI-запросов. Класс предоставляет метод
GetHardwareId(), который выполняется при первом обращении и затем возвращает
кешированное значение:

--- BEGIN CODE ---
public string GetHardwareId()
{
    if (_cachedId is not null) return _cachedId;
    string motherboard = GetMotherboardSerial();
    string cpu         = GetCpuProcessorId();
    string combined    = $"{motherboard}|{cpu}";
    byte[] hash = SHA256.HashData(Encoding.UTF8.GetBytes(combined));
    _cachedId = Convert.ToHexString(hash).ToLowerInvariant();
    return _cachedId;
}
--- END CODE ---

Метод IsUsable() фильтрует заглушки OEM-производителей (значения вида
"To Be Filled By O.E.M.", "Default string", нулевые GUID) — это обеспечивает
надёжность идентификации на широком диапазоне оборудования.

Сервис профиля пользователя (UserProfileService)

При запуске приложения LoadAsync() ищет запись HardwareRegistration с текущим
HardwareId и загружает DisplayName. Метод UpdateDisplayNameAsync() сохраняет
новое имя в БД (INSERT или UPDATE) и генерирует событие DisplayNameChanged:

--- BEGIN CODE ---
public async Task UpdateDisplayNameAsync(string name)
{
    name = name.Trim();
    if (string.IsNullOrWhiteSpace(name)) return;
    using var scope = _scopeFactory.CreateScope();
    var db   = scope.ServiceProvider.GetRequiredService<AppDbContext>();
    var hwId = _hwId.GetHardwareId();
    var reg  = await db.HardwareRegistrations
                       .FirstOrDefaultAsync(r => r.HardwareId == hwId);
    if (reg is null)
    {
        reg = new HardwareRegistration { HardwareId = hwId, DisplayName = name };
        db.HardwareRegistrations.Add(reg);
    }
    else { reg.DisplayName = name; }
    await db.SaveChangesAsync();
    DisplayName = name;
    DisplayNameChanged?.Invoke(this, name);
}
--- END CODE ---

Использование IServiceScopeFactory вместо прямой инъекции AppDbContext позволяет
создавать новый scope для каждой операции с БД — это обязательная практика
в сервисах с Singleton-временем жизни.

Сервис синхронизации файлов (SyncService)

Запрос содержимого файла реализован через TaskCompletionSource с таймаутом
15 секунд. Это позволяет await-итъ асинхронный событийный ответ от SignalR:

--- BEGIN CODE ---
public async Task<string?> RequestFileContentAsync(string token, string relativePath)
{
    if (_hub is null) return null;
    var tcs = new TaskCompletionSource<string?>();
    _pendingFiles[relativePath] = tcs;

    void Handler(object? _, FileReceivedArgs args)
    {
        if (!_pendingFiles.TryGetValue(args.RelativePath, out var pending)) return;
        _pendingFiles.Remove(args.RelativePath);
        FileReceived -= Handler;
        pending.TrySetResult(args.Base64Content);
    }
    FileReceived += Handler;
    await _hub.InvokeAsync("RequestFile", token, relativePath);
    try   { return await tcs.Task.WaitAsync(TimeSpan.FromSeconds(15)); }
    catch { _pendingFiles.Remove(relativePath); FileReceived -= Handler; return null; }
}
--- END CODE ---

Ссылка доступа имеет формат wsync://TOKEN@host:port. Метод BuildLink()
формирует её из URL сервера и токена; ParseLink() разбирает строку обратно.
Короткая 8-символьная ссылка (только токен без адреса) интерпретируется
как локальное соединение с http://localhost:5000.

Защита от path-traversal в SyncAdminSession

При сохранении файла, полученного от участника, GetSafePath() проверяет,
что результирующий абсолютный путь находится внутри разрешённой папки:

--- BEGIN CODE ---
private string? GetSafePath(string relativePath)
{
    if (string.IsNullOrWhiteSpace(relativePath)) return null;
    var safe     = relativePath.Replace('/', Path.DirectorySeparatorChar);
    var fullPath = Path.GetFullPath(Path.Combine(_folderPath, safe));
    return fullPath.StartsWith(_folderPath, StringComparison.OrdinalIgnoreCase)
           ? fullPath : null;
}
--- END CODE ---

Если участник пытается передать путь вида "../../../Windows/System32/...",
GetSafePath() вернёт null и файл не будет сохранён.

Встроенный сервер синхронизации (InProcessSyncServer)

Запуск сервера идемпотентен — повторные вызовы EnsureStartedAsync() безопасны
благодаря SemaphoreSlim:

--- BEGIN CODE ---
public static async Task EnsureStartedAsync()
{
    if (_app != null) return;
    await _lock.WaitAsync();
    try
    {
        if (_app != null) return;
        Environment.SetEnvironmentVariable("ASPNETCORE_URLS", "http://0.0.0.0:5000");
        var builder = WebApplication.CreateBuilder(...);
        builder.Services.AddSignalR(opts =>
            { opts.MaximumReceiveMessageSize = 20 * 1024 * 1024; });
        builder.Services.AddSingleton<EmbeddedSessionService>();
        ...
        await app.StartAsync();
        _app = app;
    }
    finally { _lock.Release(); }
}
--- END CODE ---

Хаб EmbeddedSyncHub реализует ту же логику маршрутизации, что и внешний
серверный хаб: перенаправляет запросы файлов и push-операции между
SignalR-соединениями через ConnectionId, хранящийся в EmbeddedShareSession.

Редактор заметок (NoteEditorPage + NoteEditorViewModel)

Инициализация редактора EasyMDE выполняется в InitializeMarkdownWebViewAsync():
WebView2 загружает HTML-страницу из встроенного ресурса или строки с
инициализированным экземпляром EasyMDE. После загрузки (NavigationCompleted)
выполняется JavaScript-функция initializeEditor().

Двусторонняя коммуникация реализована следующим образом:
- При каждом изменении в редакторе JS вызывает window.chrome.webview.postMessage(text),
  что приводит к событию QuillEditor_WebMessageReceived в C#.
- При смене активной заметки C# вызывает ExecuteScriptAsync("updateMarkdown(text)"),
  передавая HTML-содержимое.

Автосохранение происходит в обработчике WebMessageReceived: полученный текст
немедленно присваивается ViewModel.CurrentContent, что через [ObservableProperty]
запускает PropertyChanged, и при каждом изменении вызывается SaveAsync():

--- BEGIN CODE ---
private async void QuillEditor_WebMessageReceived(WebView2 sender,
    CoreWebView2WebMessageReceivedEventArgs args)
{
    string text = args.TryGetWebMessageAsString();
    ViewModel.CurrentContent = text;
    await ViewModel.SaveAsync();
}
--- END CODE ---

Метод SaveAsync() в NoteEditorViewModel формирует запись ChangeLog и сохраняет

Управление файловым деревом (FileTreeViewModel)

Метод LoadDirectory() строит иерархическое дерево FileTreeNode из объектов
DirectoryInfo и FileInfo рекурсивным обходом. Для предотвращения крашей WinUI 3
при очистке TreeView-коллекции перед очисткой все узлы сворачиваются:

--- BEGIN CODE ---
public void SafeClearTree()
{
    foreach (var node in Nodes)
        CollapseRecursive(node);
    Nodes.Clear();
}

private static void CollapseRecursive(FileTreeNode node)
{
    node.IsExpanded = false;
    foreach (var child in node.Children)
        CollapseRecursive(child);
}
--- END CODE ---

После построения дерева вызывается LoadTagsForTreeAsync(), которая для каждого
файла (.md) обращается к базе данных и загружает присвоенные ему теги.

Управление пользовательскими таблицами (DatabaseViewModel)

Метод LoadTablesAsync() формирует смешанный список: сначала добавляются четыре
встроенные «виртуальные» таблицы (Notes, Reminders, FileTags, ChangeLogs),
затем загружаются пользовательские DynamicTable из БД.

Метод LoadCustomTableAsync() десериализует SchemaJson из текущей таблицы,
формирует коллекцию ColumnDefinition, затем для каждой строки (DynamicRow)
десериализует DataJson и создаёт RowViewModel — словарь «имя столбца → значение».
Это позволяет XAML-шаблону динамически отображать произвольное число столбцов.

Переключение значения чекбокса в ячейке таблицы выполняется немедленно,
без открытия диалога:

--- BEGIN CODE ---
public async Task ToggleCheckboxAsync(Guid rowId, string columnName)
{
    using var scope = _scopeFactory.CreateScope();
    var db  = scope.ServiceProvider.GetRequiredService<AppDbContext>();
    var row = await db.DynamicRows.FindAsync(rowId);
    if (row is null) return;

    var data = JsonSerializer.Deserialize<Dictionary<string, JsonElement>>(row.DataJson)
               ?? new Dictionary<string, JsonElement>();

    bool current = data.TryGetValue(columnName, out var v) && v.GetBoolean();
    data[columnName] = JsonSerializer.SerializeToElement(!current);
    row.DataJson     = JsonSerializer.Serialize(data);
    row.UpdatedAt    = DateTime.UtcNow;
    await db.SaveChangesAsync();
}
--- END CODE ---

WinUI 3 требует, чтобы все изменения свойств, привязанных через Binding,
выполнялись в UI-потоке. Во всех сервисах и ViewModel'ах обновление

{

и файлами Markdown.

В процессе работы были решены следующие задачи:

1) Проведён анализ предметной области управления персональными знаниями;
   выявлены ключевые сущности (заметка, тег, таблица, напоминание, журнал изменений)
   и их взаимосвязи.

2) Выполнен обзор пяти существующих аналогов (Microsoft OneNote, Notion, Obsidian,
   Joplin, UpNote) и составлена сравнительная таблица, обосновывающая актуальность
   разработки собственного решения с нативным Windows UI и офлайн-хранением.

3) Сформулированы десять функциональных и семь нефункциональных требований
   к приложению.

4) Спроектирована четырёхслойная архитектура (Views → ViewModels → Services →
   Data Layer) с применением паттерна MVVM и DI-контейнера Generic Host.
   Разработана схема реляционной базы данных из девяти таблиц SQLite.

5) Реализованы 25 модулей клиентского приложения:
   - редактор заметок Markdown с WebView2 и EasyMDE;
   - конструктор пользовательских таблиц с динамической схемой на JSON;
   - раздел напоминаний с фильтрацией;
   - навигатор файловой системы с тегами;
   - экспорт заметок в PDF через QuestPDF;

6) Описан пользовательский интерфейс, реализующий гайдлайны Fluent Design System

7. Шрифт основного текста: Times New Roman 14pt, межстрочный интервал 1.5.
8. Нумерация страниц: снизу по центру, начиная с 1 (титульный лист не нумеруется).
